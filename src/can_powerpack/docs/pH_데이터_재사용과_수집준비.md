# 기존 데이터 재사용과 pH 수집 준비

## 결론과 검증 범위 (2026-10-05)

기존 데이터는 버리지 않는다. 실측 챔버 압력과 각도가 있으므로 초기 nominal 식별,
개체 비교와 잔차 크기 확인에 활용할 수 있다. 기존 계단·APRBS 데이터를 새 S1~S6
프로파일에서 얻은 데이터라고 이름만 바꾸지는 않는다. 동일한 실험 조건에서의 비교,
장착/일간 분산과 새 프로파일의 검증은 부족한 부분만 추가 측정한다.

`ph_profiles.py`는 순수 오프라인 생성기다. `ph_run_profile.py`는 기존
`RigView`, `Guard`, `Driver`, TCP 연결·패킷 형식과 압력 환산을 재사용한 별도 실행기다.
기존 압력 제어기·PID·데드존·레일 설정 및 README.md는 변경하지 않았다.

검증한 것:

- 순수 계획 테스트 47개, 실행기를 실행하지 않는 AST/컴파일 검사 3개 통과.
- 전체 세트의 CSV/JSON/PNG와 낮은 차압 S2 생성.
- 기존 데이터 4개 파일 읽기 전용 품질 검사.

검증하지 못한 것:

- 실행기 실기 운전, ROS 서비스 연결, 실제 50 Hz 송신·100 Hz 기록 및 중단 복귀.
  압력·밸브 스크립트, ROS launch/run, 토픽 발행은 실행하지 않았다.
  실행기의 `--dry-run`도 이번 작업에서는 실행하지 않았다.
- 워크스페이스 빌드: `qpoases_vendor`의 qpOASES 3.2.1 다운로드에서
  `Could not resolve host: github.com`으로 실패했다. `can_powerpack` 빌드에는 도달하지 못했다.
  기존 워크스페이스 underlay 경고도 있었으므로, 새 빌드 성공으로 해석하면 안 된다.

따라서 현재 상태는 **코드·오프라인 계획 준비, 실기 사용 전 확인 필요**다.

## 프로파일 생성 (하드웨어 접근 없음)

워크스페이스 루트에서 실행할 수 있는 순수 오프라인 명령:

```sh
python3 src/can_powerpack/scripts/ph_profiles.py --profile all --suite full --out /tmp/ph_full_new
python3 src/can_powerpack/scripts/ph_profiles.py --profile S2 --d-max 48 --out /tmp/ph_precheck_new
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q tests/test_ph_profiles.py tests/test_ph_runner_static.py
```

출력 폴더는 새 이름을 쓴다. 기존 계획을 덮어쓰지 않는다. `--no-plot`은 PNG만 생략한다.

- full: S6 시드 0~3 학습, 4~5 검증. standard: 0,1 학습, 4 검증.
  `--seed`는 이 번호들의 공통 오프셋이다. 모든 개체에 같은 파일을 쓴다.
- `suite.json`에 R0 → S2 → S1a → S1b → S3 → S5 → S4 → S6 → R0 순서와 역할·해시를 기록한다.
- JSON의 `plan.segments`가 보간·정착을 포함하는 원본 계획이며 `summary.sha256`은
  canonical JSON 계획의 해시다. `csv_sha256`은 별도의 CSV 바이트 해시다.
- 시간형 CSV는 공칭 50 Hz 표본이며 실제 실행기는 JSON의 선형/코사인 보간을 사용한다.
  정착형 CSV는 원래 목표 열에 `kind,mode,duration_s`를 추가한 세그먼트 목록이다.
  `settle`의 60 s는 고정 대기가 아니라 타임아웃이다. 그림은 타임아웃 상한을 사용한다.
- S2는 불가능한 점의 제외 목록을 남긴다. 낮은 d_max가 고정 끝점과 충돌하는 다른
  프로파일은 오류로 거절한다. 목표를 조용히 축소하지 않는다.
- S5의 문서에 없는 외곽 정점은 S3와 같은 차압 66 kPa로 계획에 명시했다.
- S6는 c∈[101.3,115], 유효 차압 영역에서 웨이포인트를 생성하고 최종 챔버 기울기로
  검사한다. 600 s 측정 구간 안에 처음 측정점으로 돌아오는 코사인 램프와 시간 맞춤
  유지 구간을 포함한다. 대기압 진입·복귀·시작/끝 5 s는 이 600 s 밖이다.

이번에 생성한 파일:

- 전체: `/tmp/ph_profiles_20261005_full/` (CSV/JSON/PNG + suite.json)
- 낮은 차압 확인: `/tmp/ph_profiles_20261005_precheck/S2_0.json` (동반 CSV/PNG)

고정 시간 예: R0 40.025 s, S3 263.192 s, S4 770.519 s, S5 110.756 s,
S6 약 630.006 s. S1a/S1b/S2는 정착 시간에 따라 달라진다.
문서의 개략 시간을 고정 실행 시간으로 사용하지 않는다.

## 실행기와 사용자 확인

기존 `pressure_id_seq.py`에는 이미 연속 기록 기능이 있다. 하지만 기본 계단 입력,
가변 각속도 허용, 추종 감시 20 kPa/10 s, 일부 시나리오의 감시 해제, 런타임 점 삭제는
새 지침과 다르다. 따라서 새 프로파일을 생성하는 것 외에 얇은 실행 계층도 필요하다.
새 실행기는 기존 코드의 읽기·전송 기반을 재사용하되 이 동작을 물려받지 않는다.

사용자용 계획 확인 예시(이번 작업에서는 실행하지 않음):

```sh
python3 src/can_powerpack/scripts/ph_run_profile.py /tmp/ph_profiles_20261005_precheck/S2_0.json --dry-run --actuator 1 --mount 1 --d-max 48
```

`--actuator`는 대장의 숫자 ID 1~4를 사용한다. A01 별칭이나 5~10번 보정은 추측하지 않는다.
실기 실행에는 사용자가 실제 장착 ID·장착 횟수를 선택하고 `--confirm-preflight`와
실제로 쓴 `--launch-command`를 제공해야 한다. 이 확인 옵션은 안전 인증이 아니다.

송신 전 확인 항목:

- 새 워크스페이스 빌드와 올바른 환경, `control_mode:=0 axis:=0`, 단일 TCP 송신기.
- 해당 ID의 엔코더를 함께 장착하고 물리 0°/90° 보정을 확인.
  1축 현재 기본 YAML 29000/9000은 3번 개체 값이다.
  CanBridge는 시작할 때 환산 계수를 만든다. 실행 중 파라미터 값만 바꿔도 실제 환산이
  바뀐다고 가정하지 말고, 올바른 설정으로 재기동한 뒤 확인한다.
- 레일 목표 200/30과 챔버 대기압 준비는 사용자가 기존 절차로 수행.
  실행기는 레일을 설정하지 않는다. 초기 레일은 목표 ±8 kPa를 요구하며,
  챔버는 대기압 ±4 kPa여야 한다. 조건 불충족 시 프로파일을 잘라 실행하지 않는다.
- 실제 bridge/controller 파라미터를 읽어 보정·모드·채널 매핑을 확인하고 저장한다.
  launch 명령은 사용자 선언으로 구분하며 소스 YAML과 실제 파라미터를 모두 보존한다.
  현재 프로세스의 압력 제어 기준이 f3cd4af인지도 사용자가 확인해야 한다.

센서 결측/비유한값은 즉시 중단하고, ROS 각도·압력 배열 무수신 1 s도 중단한다.
이는 개별 CAN 보드의 프레임 나이를 증명하지 않는다. 새 과압 가드는 추가하지 않았다.
센서 감시 후 각도·속도·진동·추종 감시는 기존 Guard에 새 지침 값을 명시해 사용한다.

정상 종료는 계획 안의 복귀·5 s 대기압 유지 후 닫는다. 중단은 챔버별 최대 4 kPa/s로
대기압 복귀 후 5 s 송신을 시도한다. 종료 중 ROS/기록 오류와 TCP 송신 실패는 분리해
메타에 남긴다. TCP 단절 후 복귀는 보장할 수 없다. `target_send_complete`는 실측
대기압 도달 여부가 아니며 종료 실측 압력·나이를 별도로 본다.

실행기 코드는 정적 검토만 했다. 50/100 Hz는 공칭값이며 실제 간격 통계를 메타에 남긴다.
실기 확인 없이 이 준비 문서나 테스트 통과를 운전 허가로 사용하지 않는다.
