# 데드존 측정 → 채널 PID 튜닝 절차

밸브의 데드존(열리기 시작하는 지령값)은 **날마다·개체마다 다르고, 한 번 돌리는
9분 동안에도 3~5 %p 밀린다**(20260911_165122 실측). 그래서 "표를 다시 재고 →
게인을 확인" 하는 이 순서를 통째로 다시 도는 것이 기본이다.

여기서 쓰는 축 번호는 **사람이 부르는 번호(1~6)** 이고, yaml 의 `chN` 은 0부터다.
`ch0~ch5` = 양압 1~6축, `ch6~ch11` = 음압 1~6축.

---

## 0. 왜 이 순서인가

제어기는 밸브 모델을 쓰지 않는다. 채널 지령은 이 한 줄이 전부다.

```
u_hw = max(0, 데드존표(차압) − 여유) + u_pid
u_pid = kp·e + ki·∫e + kd·ė + kv·dP_ref/dt
```

- **데드존 표**가 밸브를 "막 열리기 직전"까지 데려다 놓는다. 이게 틀리면
  게인을 어떻게 잡아도 안 된다.
- 표가 **진짜 크래킹보다 높으면**(과보상) 어떤 지령으로도 유량 0 을 못 만들어
  릴레이 진동(뱅뱅)이 난다.
- 표가 **낮으면**(과소보상) 적분이 그 데드밴드를 매번 건너야 해서 굼뜨고,
  방향이 바뀔 때마다 오차가 크게 벌어진다.
- 그래서 **표 → 여유 → 게인 → kv** 순서다. 뒤엣것으로 앞엣것의 오차를 못 고친다.

## 1. 데드존 측정

### 원리
레일과 챔버의 **차압을 고정**해 놓고 밸브 지령을 조금씩 올려, 압력이 유효하게
움직이기 시작하는 지령을 그 차압에서의 데드존으로 기록한다. 차압을 바꿔 가며
반복해 `차압 → 데드존` 표를 만든다. 유량은 차압에 거의 비례하므로 데드존도
차압에 따라 달라진다 — 상수 하나로는 못 쓴다(음압 atm 은 상류가 대기로 고정인데도
차압에 따라 18 %p 변한다).

### 명령

```zsh
cd ~/claude_tutorial
python3 src/can_powerpack/scripts/valve_deadzone.py --axes all --repeat 5
```

- `--axes all` : 12채널 한 번에. 양압 6축 → 음압 6축 순서로 돈다.
- `--repeat 5` : 차압 한 점당 5회. 회차 표준편차가 그대로 표의 불확도이고,
  아래 **여유**를 정하는 근거가 된다.
- **레일 압력은 실제 운전에서 쓸 값으로 맞춰 놓고 재라.** 낮은 레일에서 재고
  높은 레일에서 쓰면 안 맞는다(20260911: 레일 197 에서 잰 표를 145 에서 썼더니
  +4.7~7.2 %p 어긋나 양압 3·4·6축이 아예 안 움직였다).
- 예열은 하지 않는다. 어차피 운전 중에 계속 밀리므로 "차가운 상태 기준 + 작은
  여유" 가 실측상 더 낫다.

결과는 `~/result/deadzone_<타임스탬프>/` 에 원본 샘플과 함께 남는다.

### 표 반영

```zsh
python3 src/can_powerpack/scripts/valve_deadzone.py --from ~/result/deadzone_<타임스탬프> --write
```

- 3~4차 다항식으로 피팅하고 차수는 LOO-CV 로 고른다.
- `--write` 는 yaml 의 `valve_deadzone:` 과 `channel_config:` **전체를 다시 쓴다.**
  손으로 적어 둔 값이 있으면 날아간다. 쓰기 전에 백업이 자동으로 생기지만
  (`powerpack_config.yaml.bak.<타임스탬프>`), 쓰고 나서 아래를 꼭 확인할 것:
  - `park_enable` / `park_below_pct` 가 살아 있는지
  - `margin_*_pct` 와 `channel_config.chN.pid` 가 살아 있는지

### 확인

```zsh
grep -A3 "valve_deadzone:" src/can_powerpack/config/powerpack_config.yaml
```
노드를 띄우면 기동 로그에 채널마다 `데드존 xx.x~xx.x%(dp nn~nn, 13점)` 이 찍힌다.
`(상수)` 라고 나오면 표가 안 실린 것이다.

## 2. 여유 (margin) 정하기

```
실제 지령 = 표(차압) − 여유
```

여유는 **표의 불확도보다 작게** 잡는다. 크게 잡으면 데드밴드가 넓어져 적분이
매번 건너야 하고, 그게 곧 느린 응답과 반전 오차가 된다.

실측으로 확인된 것(20260911_165122):

| 여유 | 축 | 9분 뒤 RMSE |
|---|---|---|
| 1.0 | 양압1·5 | 0.31 / 0.82 |
| 2.0 | 양압4 | 1.71 |
| 3.0 | 양압3·6 | 1.56 / 1.19 |

**나빠진 순서가 여유 순서와 정확히 일치한다.** 여유를 올려서 채터를 잡으려 한
시도는 두 번 다 역효과였다. 기본 `valve_deadzone.margin_pct: 1.0` 을 쓰고,
특정 축만 빠른 채터(아래 **전환/s** 15 이상)가 나면 그 축만 2.0 으로 올린다.

왜 여유가 작아야 하나: 운전 중 밸브가 무거워져 필요한 지령이 micro·atm **양쪽 다**
올라간다. 부호 하나짜리 `u_pid` 로는 양쪽을 동시에 못 메우므로 **대칭 데드밴드**가
생긴다. 여유는 거기에 그대로 더해진다.

## 3. 파킹 확인

```yaml
valve_deadzone:
  park_enable: true
  park_below_pct: 5.0
```

쉬는 밸브를 0 이 아니라 "가장 낮은 데드존보다 5 %p 아래" 에 세워 둔다. 코일 전류가
미리 서 있어 지령이 들어올 때 상승 시간이 줄고, 채터가 눈에 띄게 준다
(A/B 실측: 전환/s 0.8~8.3 켬 vs 7.2~17.4 끔).

`--write` 가 이 두 줄을 지운 적이 있으니 표를 다시 쓸 때마다 확인할 것.

## 4. 게인 튜닝

### 먼저 레일이 안정한지 본다

**채널 게인을 만지기 전에 레일부터 본다.** 레일이 떠다니면 12채널이 전부
동시에 나빠지고, 그걸 채널 게인 탓으로 오해하게 된다.

- 양압 레일 목표 `LinePID.pos.ref` 는 **도달 가능한 값**이어야 한다. 6축 동시
  운전에서 200 은 불가능하고(방출 밸브가 4.7 % 로 닫힌 채 레일이 148±8.4 로
  떠다녔다) 145 는 방출 밸브가 ~50 % 에서 조절하며 ±0.6 으로 잡힌다.
- 기동 후 레일이 목표에 붙는 시간이 **10~35 초**면 정상이다. 50 초 넘게 걸리거나
  챔버 목표보다 낮게(양압에서 130 미만) 내려가면 `LinePID.pos.kp` / `i_limit` 문제다.
- 로그로 확인: 컬럼 `p_line_pos_kpa`, `pwm_pct_line_pos`.

### 판정에 쓰는 지표

로그 `~/result/<ts>/<ts>.csv` 에서 채널마다:

| 지표 | 뜻 | 목표 |
|---|---|---|
| RMSE | 전체 추종 오차 | < 0.5 kPa |
| 최대 \|e\| | 최악 순간 | < 2 kPa |
| **저주파 잔차** (<0.5 Hz) | 지연·이득 부족 | 작을수록 |
| **고주파 잔차** (≥0.5 Hz) | 채터·이득 과다 | 작을수록 |
| **전환/s** | micro↔atm 이 뒤바뀐 횟수 | < 10 |

**진단은 이 둘의 비율로 한다:**
- 고주파 ↑ · 전환/s ↑ → 이득 과다 또는 **표 과보상** → 여유를 올리거나 게인을 내린다
- 저주파 ↑ · 전환/s ↓ → 이득 부족 또는 **여유 과다** → 게인을 올리거나 여유를 내린다
- 오차 스펙트럼에 기본파가 아닌 **뚜렷한 봉우리**(예 0.2 Hz)가 있으면 한계주기다.
  비례 권한이 모자라 적분 혼자 데드밴드를 건너는 것이니 **kp 를 올린다**(내리지 말 것).

### 게인 우선순위

yaml 은 6단으로 겹친다. 뒤가 앞을 덮고, **없는 키는 앞 단계가 남는다.**

```
ChannelPID.*
  → ChannelPID.{up,down}.*
    → ChannelPID.{pos,neg}.*
      → ChannelPID.{pos,neg}.{up,down}.*
        → channel_config.chN.pid.*
          → channel_config.chN.pid.{up,down}.*
```

`up` = 압력을 올리는 방향, `down` = 내리는 방향. 양압은 올릴 때 micro,
음압은 올릴 때 atm 이다.

**축마다 따로 튜닝하지 말고, 가장 좋은 축의 값을 나머지에 복사하는 것으로 시작하라.**
축별로 낮춰 놓은 게인이 쌓이면 나중에 왜 그 값인지 알 수 없게 되고, 실제로
20260911 에 낮게 눌러 둔 축들이 전부 최하위였다. 같은 하드웨어면 같은 게인이 맞다.

### 현재 값 (20260911 기준)

```yaml
ChannelPID:
  kp: 0.6       kp_far: 0.6    kp_break_kpa: 3.0
  ki: 2.0       ki_far: 1.0    kd: 0.03
  i_limit_pct: 8.0             i_deadband_kpa: 0.0
  i_reset_on_step_kpa: 1.0
  gain_dp_ref_kpa: 60.0        gain_scale_min: 0.6   gain_scale_max: 2.0
  pos:
    down: { kp: 1.5, kp_far: 1.2 }
```
양압 2~6축(`ch1`~`ch5`)은 `kp 0.3 / ki 0.95 / down kp 0.82 / ki 1.1` 로 맞춰 놓았다.

## 5. 레퍼런스 속도 피드포워드 (kv)

```
u_pid += kv · dP_ref/dt        (차압 보정 gs 를 같이 곱한다)
```

**사인 방향이 바뀔 때 생기는 오차는 이걸로 잡는다. 적분 리셋으로는 못 잡는다.**

이유: 사인을 따라가는 데 필요한 지령은 오차가 아니라 **목표의 속도**에 비례한다
(유량 ∝ 개도, dP/dt ∝ 유량). PI 는 그 지령을 적분으로만 만들 수 있어서 항상
오차가 먼저 생겨야 한다. 반전 구간이 최악인 게, 지령이 한쪽 밸브 데드존에서
반대쪽 데드존까지 통째로 건너야 하는데 그 구간의 오차는 0 근처라 적분이 기어간다.
실측(20260911_170834): 반전 후 3~4 초 동안 오차가 −3.0 ~ +2.4 kPa 까지 벌어졌다.

**적분을 리셋하면 안 되는 이유**: 반전 시점의 적분은 "직전 동작점의 유물" 이 아니라
**데드존 표의 오차를 보상하고 있는 실값**이다(운전 중 3~5 %p 밀린다). 버리면 그
보상까지 잃고 새 과도가 생긴다.

### kv 크기 정하는 법

`kv ≈ 1 / (플랜트 기울기 [kPa/s per %p])` 인데, 로그에서 직접 재는 쪽이 정확하다:

1. 데드존 표를 빼서 `u_pid` 를 복원한다
   (`u_pid = 활성 밸브 지령 − (표(차압) − 여유)`)
2. `u_pid` 의 **진폭**을 `dP_ref/dt` 의 진폭으로 나눈다
   (표 오차는 DC 라 진폭에 안 들어간다 — 그래서 이 방법이 표에 무관하다)

20260911_172023 실측:

| | ch0 | ch1 | ch2 | ch3 | ch4 | ch5 | 중앙값 |
|---|---|---|---|---|---|---|---|
| 양압 | 3.50 | 3.23 | 2.81 | 2.85 | 3.84 | 3.42 | **3.33** |
| 음압 | 3.48 | 2.04 | 1.67 | 2.18 | 2.47 | 2.04 | **2.11** |

### ★ 함정 — 위에서 잰 값은 **실효값**이다 (yaml 값이 아니다)

ff 에도 차압 보정 `gs = clamp(gain_dp_ref_kpa / 차압, 0.6, 2.0)` 가 곱해진다.

```
실효 kv = gs × (yaml 의 kv)
```

이 동작점(레일 145, 챔버 110~130)에서는 **gs 가 상한 2.0 에 붙어 있다**:
양압 micro 차압 15~35, atm 차압 9~29 → `60/dp` 가 1.7~6.7 이라 전부 clamp 된다.

그래서 위 표의 "필요량 3.33" 을 yaml 에 그대로 쓰면 **2배 과하다.**
`yaml kv = 필요량 / gs = 3.33 / 2.0 ≈ 1.7` 이다.

실제로 이걸 놓쳐서 한 번 크게 망쳤다(20260911_173225): yaml 2.7/4.0 = 실효 5.4/8.0
으로 넣었더니 양압 RMSE 0.25 → 3.60, 최대오차 15.9 kPa 가 됐다. 음압은 거의
그대로여서 "양압만 동시에 나빠짐 = 양압 전용 파라미터" 로 범인을 좁힐 수 있었다.

**현재 1.0/1.5 는 실효 2.0/3.0 으로 이미 필요량 근처다.** 20260911_172023 에서
반전 오차가 1.68 → 1.60 밖에 안 준 것은 ff 가 모자라서가 아니라 **이미 거의
맞았기 때문**이고, 남은 반전 오차는 ff 로는 더 못 줄인다. 다시 건드릴 거면
yaml 기준 1.7 을 넘기지 말 것.

### 현재 값

```yaml
ChannelPID:
  kv: 1.0                # 실효 = gs(≈2.0) × 1.0 = 2.0
  ref_rate_tau_s: 0.3    # 목표는 10 Hz 계단으로 들어온다 — 미분 전 반드시 저역통과
  ff_limit_pct: 15.0
  pos:
    down: { kv: 1.5 }    # 배기는 %p 당 유량이 충전의 1/3 → 실효 3.0
```

`ref_rate_tau_s` 를 0 으로 두면 안 된다. 목표가 10 Hz 로 들어오고 제어는 500 Hz 라
그냥 미분하면 100 ms 마다 55 kPa/s 스파이크가 나와 밸브를 때린다. 0.3 s 가 사인
0.025 Hz 에 주는 위상 지연은 2.7° 뿐이다.

**조정법**: 반전 오차가 **원래 진행 방향으로** 남으면 kv 를 올린다. 반전에서
**반대쪽으로 넘치면** 내린다.

## 6. 검증 실행

```zsh
# 기본 — 진폭 20, 주기 40 s, 3주기, 12채널 동시
python3 src/can_powerpack/scripts/pressure_sweep_server.py \
  --axes all --sweep sine-diff --sine-amp 20 --sine-period 40 --sine-cycles 3 \
  --sine-center-pos 120 --sine-center-neg 60

# 여러 동작점·진폭·주기를 한 번에 (6구간, 약 8.6분)
python3 src/can_powerpack/scripts/pressure_sweep_server.py --axes all --sweep sine-scan

# 주기 스캔 — 압력 범위를 고정하고 주기만 점점 빠르게 (끊김 없이 연속)
python3 src/can_powerpack/scripts/pressure_sweep_server.py \
  --axes all --sweep sine-freq --sine-amp 40 \
  --sine-center-pos 128 --sine-center-neg 66
```

`sine-freq` 는 진폭·동작점을 고정하고 주기만 줄인다. 요구 기울기가
`pi·진폭/주기` 라 주기를 반으로 줄이면 기울기가 두 배다 — 어느 기울기에서
추종이 무너지는지를 한 로그에서 본다. 파형이 `(1−cos)/2` 라 모든 구간이
`중앙값 − 진폭/2` 에서 시작·종료하고 그 점의 기울기가 0 이므로, 구간 사이에
아무것도 넣지 않아도 값·기울기가 이어진다. 진입/복귀 램프는 맨 앞뒤에 한 번씩만
둔다. **마지막에 첫 주기를 한 번 더 도는 것이 기본**이다 — 데드존 표류와 주파수
영향을 분리하려면 처음과 끝의 같은 주기를 비교해야 한다 (`--no-freq-recheck` 로 끔).

**비교할 때 주의**: 데드존이 운전 중에 밀리므로 **9분짜리와 3분짜리는 뒷부분 숫자가
다르다.** 전후 비교는 반드시 같은 길이·같은 시나리오로 하고, 레일이 정착한 뒤
구간(보통 t > 50 s)만 본다. 기동 직후 40 초는 레일 과도라 게인 판단에 쓰면 안 된다.

---

## 7. 흔한 함정

| 증상 | 원인 | 확인 |
|---|---|---|
| 모든 채널이 동시에 나빠짐 | 레일 또는 표. 게인 아님 | `p_line_pos_kpa` 먼저 |
| 기동 후 40 초가 유난히 나쁨 | 레일 과도 | 정상이다. t>50 s 만 보라 |
| 한 채널만 뱅뱅 | 표 과보상 또는 kp 부족 | 오차 스펙트럼에 봉우리가 있으면 kp 부족 |
| yaml 을 고쳤는데 안 먹음 | 정수로 썼다(`margin_pct: 3`) | 항상 `3.0` 으로 |
| 로그에 짧은 진동 | `pp_controller` 가 두 개 떠 있다 | `pgrep -af pp_controller` |
| 옛 바이너리가 돈다 | `src/can_powerpack/` 안에 build/install 트리 | 워크스페이스 **루트**에서 빌드 |
| `--write` 후 설정이 사라짐 | 스크립트가 매핑 전체를 다시 쓴다 | 위 1번의 확인 목록 |
| kv 를 올렸는데 양압만 폭주 | `gs` 가 상한 2.0 이라 실효값이 2배 | 5장의 ★ 함정 |
| **한쪽(양압/음압)만 나빠짐** | 그 쪽 전용 파라미터. 공통 파라미터 아님 | `ChannelPID.pos.*` 부터 |

## 8. 한 번에 다시 도는 전체 순서

```zsh
cd ~/claude_tutorial

# 1) 실제 운전 레일로 맞춘 상태에서 12채널 데드존 측정
python3 src/can_powerpack/scripts/valve_deadzone.py --axes all --repeat 5

# 2) 피팅해서 yaml 에 반영
python3 src/can_powerpack/scripts/valve_deadzone.py --from ~/result/deadzone_<ts> --write

# 3) 여유·파킹·게인이 살아 있는지 확인
grep -E "margin_pct|park_enable|park_below_pct" src/can_powerpack/config/powerpack_config.yaml

# 4) 빌드 (반드시 루트에서)
source /opt/ros/humble/setup.zsh
colcon build --packages-select can_powerpack --cmake-args -DCMAKE_BUILD_TYPE=Release

# 5) 검증 실행 — 레일 정착 시간부터 본다
python3 src/can_powerpack/scripts/pressure_sweep_server.py \
  --axes all --sweep sine-diff --sine-amp 20 --sine-period 40 --sine-cycles 3 \
  --sine-center-pos 120 --sine-center-neg 60
```

표만 다시 쟀으면 게인은 그대로 두고 5번부터 판정하면 된다. 표가 맞으면 게인은
잘 안 바뀐다 — 지금까지 게인을 고쳐야 했던 경우는 전부 표나 레일이 원인이었다.
